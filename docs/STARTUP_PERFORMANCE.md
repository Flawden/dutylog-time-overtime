# Запуск приложения: устранение лишнего ожидания

База: 860edc421ec3f4c065728a006a068defcc60b4c8 (принятый MOBILE).

При открытии календаря legacy init ожидал loadLedgerPage, который при наличии
Vue владельца загружал весь банк времени. На staging time-compensation занимал
4179 мс. Теперь этот пакет загружается при входе в соответствующий Vue раздел.
Legacy fallback сохраняет прежний запуск. Баланс календаря приходит в его bundle.

После проверки сессии и модулей независимые справочники, профиль и статус
синхронизации запрашиваются параллельно. Promise.allSettled дожидается всех
запросов и затем передаёт ошибку обычному обработчику; поздние записи не обгоняют
первую календарную проекцию. Профиль с рабочей зоной по-прежнему загружен до неё.

Service worker отдаёт публичные файлы /vue/chunks/ с хешем содержимого из
текущего release cache без сети. HTML и файлы со стабильным URL остаются
network-first; API, вход и выход не перехватываются. Кэш предыдущей сборки
удаляется при активации нового worker. Первый запуск после обновления требует
загрузки файлов; ускорение кэша проявляется при последующих открытиях.

Браузерные регрессии проверяют параллельные запросы на искусственно медленной
сети, отсутствие time-compensation при открытии календаря, загрузку при переходе
в overtime, cache-first для immutable chunk и свежую серверную идентичность.

Это первый шаг ускорения всего сайта. Повторные проекции календаря и чтения
контекста времени ещё требуют отдельного профилирования. Снимок CPU/RAM после
загрузки не исключает кратковременную нагрузку. Итоговые секунды на телефоне
нужно измерить после staging deploy; обещание конкретного времени не даётся.
Персональный offline snapshot до проверки пользователя не открывается этим
изменением; формат IndexedDB и финансовые расчёты не меняются.
