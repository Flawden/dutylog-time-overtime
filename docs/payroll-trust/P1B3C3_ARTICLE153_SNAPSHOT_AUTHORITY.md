# P1B3C3 — сохранение оснований статьи 153 в ревизии Payroll

База: P1B3C2, commit `8d965c37013710a49a8084017a216813c1a2bc9d`.
Схема: `ARTICLE153_AUTHORITY_SNAPSHOT_V1`; миграция PostgreSQL V86.

## Граница этапа

C3 добавляет внутренний механизм сохранения источников и решений в новой
ревизии `PayrollSnapshot`. Это `AUTHORITY_ONLY`, не итоговая сумма HOLIDAY_PAY.
В существующий PayrollService механизм пока не включён. Текущие расчёты,
начисления за сверхурочную работу и пользовательские маршруты не меняются.

Следующий этап должен связать этот механизм с полноценным созданием ревизии:
включить fingerprint оснований в идентичность расчёта, сохранить окончательные
денежные строки и применённые формулы/округления, проверить их согласованность,
затем отдельно разрешить HOLIDAY_PAY. Наличие этой таблицы само по себе не
означает завершённую интеграцию начисления или готовность производственного расчёта.

## Что сохраняется

Для каждого квалифицированного фрагмента фиксируются:

- физический источник: тип и ID, начало/конец, часовой пояс, минуты;
- причина PUBLIC_HOLIDAY / EMPLOYEE_REST_DAY / BOTH, юридические источники
  праздничного дня и источник индивидуального графика;
- норма месяца, положение относительно нормы, отработанные минуты и fingerprint;
- режим оплаты, историческая ставка, исходный оклад/тариф, валюта, дата и ID условия;
- решение по заявлению на другой день отдыха с полным фактом заявления;
- решение уже существующей B1 policy с версией и нормативными ссылками;
- местное основание повышенной оплаты, дата/ID pricing term и HOLIDAY rules;
- решения INCLUDE/EXCLUDE по версиям компонентов, их формулы и источники C2.

BOTH остаётся одной причиной одного фрагмента и не удваивает количество.
Снимок не содержит ссылок на изменяемые JPA-объекты внутри JSON.
Хеш SHA-256 защищает от случайной порчи/подмены тела относительно envelope;
он не является электронной подписью и не защищает от администратора,
способного одновременно переписать JSON и хеш.

## Атомарность и согласованность

`createRevision` принимает только новую, ещё не сохранённую ревизию закрытого
периода. Повторное прикрепление текущих оснований к историческому расчёту запрещено.
Родитель и документ сохраняются одной транзакцией REPEATABLE_READ. Присоединение
к более слабой транзакции отвергается. Блокирующий источник прерывает операцию;
ошибка после вставки родителя откатывает обе записи.

Проверяются месяц и единица количества, отсутствие перекрытий внутри одного
события, принадлежность источников владельцу, согласованность условий оплаты
с ревизией, fingerprint полного события заявления и HOLIDAY pricing rules.
Новые записи привязаны к ID/владельцу/месяцу/номеру/хешу/валюте ревизии и
временным отметкам закрытия и проверки источника.

Таблица имеет один документ на snapshot_id, внешний ключ без каскадного удаления.
JPA-сущность неизменяемая; публичного API обновления документа нет.
Миграция не заполняет старые ревизии данными из текущих справочников.

## Чтение истории

`load(owner, snapshotId)` обращается только к сохранённому документу и его
PayrollSnapshot. Живые authority services и текущая policy не вызываются.
Владелец ограничивает запрос. Проверяются версия схемы, SHA-256, связь с ревизией,
количество фрагментов, сумма минут и обязательные разделы документа.

Отсутствующий документ — неизвестная/старая история (`Optional.empty`), не
подтверждённый ноль. Сохранённый пустой результат означает ноль по источникам,
доступным существующему resolver в момент сохранения. Пустой список компонентов
не подтверждает полноту реальной системы оплаты работодателя (ограничение C2).

## Проверки перед закрытием

Локально: Article153Snapshot*Test, release-check, полный clean verify и JaCoCo
с исходными порогами 70% branches / 88% instructions. Тесты покрывают реальные
запись/чтение через JPA, откат, изоляцию владельцев, запрет backfill, независимость
истории от live capture, повреждение документа, выбор отгула, почасовую оплату,
оклад и BOTH. Локальная база тестов — H2; применение V86 в PostgreSQL проверяется
staging workflow. Завершение этапа подтверждается только после review result ZIP
с точным commit/tree и staging, включая фактический deploy/smoke шаг.
