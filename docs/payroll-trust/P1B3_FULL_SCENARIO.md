# P1B3 — полный сценарий после C4C

База: `6984ee14a958ae998c362f16eeab2519aaf22b22`. Это завершение проверки
C4A → C4B → C4C, а не новая формула оплаты или новая цепочка дробных этапов.

## Что получает пользователь

Стандартные ответы Payroll preview/calculate/history содержат `article153`:

- `REVIEWED`: подтверждённые минуты (один раз), праздничная доплата по тарифу,
  праздничная доплата по компонентам и сохранённая ночная доплата.
- `REVIEW_BLOCKED`: причина блокировки; минуты и денежная расшифровка `null`,
  частичные неподтверждённые деньги не выдаются за подтверждённые.
- `LEGACY_UNREVIEWED`: прежняя формула по настроенным правилам, без утверждения
  о подтверждённых основаниях праздничной оплаты. Денежная расшифровка `null`.

Все суммы расшифровки уже входят в `ordinaryPremiumPayMinor` и итог зарплаты.
Браузер только форматирует их. Он не выбирает коэффициенты, не округляет
праздничную оплату заново и не добавляет расшифровку к итогу второй раз.

История читает существующие C3/C4A/C4B2/C4C frozen документы с проверкой хэшей
и связей. Она не обращается к действующим правилам или pricing engine. Изменение
условий блокирует новую ревизию до обновления review; старые суммы и основания
остаются прежними. Повреждённый frozen документ вызывает ошибку, а не метку legacy.

Новые endpoint, формы подтверждения оснований и миграции не добавлены. Источники
review и выбора компенсации остаются в существующих domain services. Это проверка
и отображение имеющегося пути; пользовательская форма ввода review ещё отсутствует.

## Проверка реальной цепочки

`Article153PayrollScenarioTest`: изолированная H2, реальный MockMvc/Spring API,
реальные смены, actual-work interval с часовыми границами, юрисдикция, федеральный
праздник 9 мая 2026, отдельный payroll-effect календаря, compensation/pricing,
классификация компонентов, полный review, closed period, snapshot и frozen history.
Ни один domain bean не подменяется. Документы-основания в тестах явно synthetic.

| Сценарий | Результат (копейки RUB) |
| --- | --- |
| 60 минут, 50000/час; локальная праздничная +50%, statutory floor +100%, ночная +5% | база 50000 + праздничная 50000 + ночная 2500 = 102500 |
| INCLUDE-компонент 12500/час с праздничной доплатой +100% | база 50000 + обычный компонент 12500 + праздничная 62500 + ночная 2500 = 127500; минуты 60 |
| Премия 40% и районный коэффициент 15% | премия 41000 от 102500; коэффициент 21525 от 143500; итог 165025 |
| Выбран другой день отдыха | праздничная доплата 0; ночная 2500 сохранена; итог 52500 |
| Ставка изменена до 60000/час | stale review блокирует новую ревизию; после нового review итог 123000, новая ревизия/хэш |
| Review отсутствует | legacy итог 77500; status LEGACY_UNREVIEWED; payable sidecar отсутствует |
| Чужой пользователь | история и подтверждённая расшифровка не раскрываются |
| Повреждённый frozen документ | отказ чтения, без fallback |

Браузерные `payroll-article153-display.spec.js` используют явно помеченные fixtures
ответов API для проверки двух представлений: preview/history с разными сохранёнными
суммами и заблокированная кнопка с понятной причиной. Эти fixtures не заменяют
реальную domain/API проверку выше. Существующий browser holiday сценарий также
проверяет, что legacy-оплата не получает метку REVIEWED.

## Границы завершения

Подтверждение применимо только к месяцу с C4B1 review. Новая форма certification
не входит в этот выпуск. Непроверенные legacy месяцы не объявляются юридически
подтверждёнными. Даты денежных агрегатов за несколько дней не распределяются
выдуманным способом; отдельные требования среднего заработка этим не закрываются.

Локальные Java/H2 и Chromium проверки не заменяют clean PostgreSQL и фактический
staging deploy/smoke. Runner ожидает CI для точного pushed commit; итоговое принятие
требует RESULT-архив. Production автоматически не публикуется.

## Окружение тестов

Java/H2 запускаются с `TZ=UTC`, как в предыдущих proof и staging.
Рабочие часовые пояса пользователя остаются явными domain facts (в частности,
существующий тест исторической коррекции проверяет реальный переход UTC → Berlin
через DST и уменьшение перерыва со 120 до 60 минут).

Первый полный локальный прогон с унаследованным `TZ=Europe/Bucharest` выявил
зависимость старого `ActualExplicitBreakTimezoneCorrectionTest` от системного
часового пояса при сохранении/чтении локальных времён в H2. Сам код этой подсистемы
совпадает с принятой базой C4C; отдельный прогон в UTC проходит. Пороги покрытия,
проверки DST и assertions не менялись и не пропускаются. Тестовое окружение runner
явно фиксировано; это не исправление работы JDBC в произвольном системном поясе.
