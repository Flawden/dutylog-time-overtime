# P1B3C4B2 — денежные суммы из подтверждённой системы оплаты

База C4B1: `44613c3a02b4e6068f7763326d8a75568f101817`. PostgreSQL V89.
Формат: ARTICLE153_REMUNERATION_SNAPSHOT_V1, scope REMUNERATION_REFERENCE_ONLY.

## Результат

C4B2 завершает денежную часть C4B: создаёт три отдельные справочные суммы и строки
из уже сохранённых C3/C4A и точной подтверждённой ревизии C4B1:

* STATUTORY_TARIFF_REFERENCE — тарифная часть сохранённого B1 статутного решения;
* APPLICABLE_LOCAL_TARIFF_REFERENCE — местная тарифная оценка с учётом явной
  применимости при отгуле из C4B1;
* COMPONENT_REFERENCE — сумма дополнительных частей INCLUDE-компонентов.

Тарифные оценки — альтернативные основания последующего согласования. Их нельзя
складывать между собой и с базовой оплатой как готовую зарплату. Компонентные
строки не выводятся из имени, общего процента настройки или решения INCLUDE.
Источник суммы за период, знаменателя и дополнительной кратности — C4B1.
Окончательная сумма HOLIDAY_PAY этим выпуском не определяется.

## Арифметика и округление

Существующий PayPricingEngine расширен country-neutral методом
pricePeriodPremium(periodAmountMinor, periodMinutes, minutes, additionalBps).

`periodAmountMinor × minutes × additionalBps / (periodMinutes × 10000)`

BigDecimal, одно HALF_UP до целой денежной единицы, longValueExact. Метод возвращает
только дополнительную часть. Старая часовая арифметика использует тот же метод
со знаменателем 60 и сохраняет прежний результат.

При месячной сумме 10000 коп., знаменателе 9600 минут, 60 минутах работы и +10000 BPS
результат — 63 коп. Промежуточной часовой ставки с округлением нет.
Два фрагмента по 30 минут с одной суммой/знаменателем/BPS образуют одну группу.
При сумме 1 коп./час и +10000 BPS результат 1 коп., а не 2.
Разные компоненты и разные BPS образуют разные группы. Если кратность при отгуле
и при усиленной оплате совпадает, их фрагменты объединяются по экономическому
ключу, но ссылки на исходные фрагменты сохраняются.

Ключ хранит вид оценки, ID версии компонента (0 для тарифа), период, сумму за
период, знаменатель и BPS. Строка хранит минуты, сумму и индексы/минуты C3.
Нули при явной дополнительной кратности 0 сохраняются как строки, не как
отсутствие подтверждённых данных. Переполнение отклоняется.

## Выбор работника и полнота

Для каждого фрагмента используется сохранённый compensationChoice из C3.
Для INCLUDE выбирается enhancedAdditionalBps либо restDayAdditionalBps из C4B1.
Для местного тарифа при OTHER_REST_DAY и NOT_APPLICABLE ставка справочной строки
равна 0. APPLIES сохраняет местный BPS из C3. При ENHANCED_PAY используется
сохранённый местный BPS. Статутный BPS берётся из C3 без новой policy-интерпретации.

Каждый INCLUDE должен иметь ровно одно подтверждённое правило с тем же ID версии,
SHA-256 компонента и владельцем. EXCLUDE не получает денежной строки. Лишнее,
пропущенное или чужое правило, иной месяц, повреждённый источник и неполное
подтверждение блокируют создание всей ревизии.

## Атомарность и история

Article153RemunerationSnapshotService.createRevision создаёт новый PayrollSnapshot,
C3, C4A и C4B2 в одной REPEATABLE_READ-транзакции. C3 проверяет новый draft и уровень
корневой транзакции. После захвата источников C4B1 resolver подтверждает месяц и
каждую дату C3; все должны ссылаться на одну точную ревизию источника. Источник
читается по owner + ID, а не принимается как произвольный JSON от вызывающего.

Ошибка после вставки C3/C4A откатывает всю цепочку snapshot. C4B1 подтверждение
остаётся самостоятельным неизменяемым источником. Внутримесячный дрейф источников
блокирует создание, а не выбирает случайную ревизию.

load(owner, snapshotId) читает только сохранённые C4B2/C4A/C3 и указанную ревизию
C4B1. Он не выбирает текущую ревизию правил, не вызывает resolver, policy или
денежный движок. SHA-256, заголовки, суммы, группы и точные источники проверяются;
денежные результаты не пересчитываются. Исправление C4B1 применяется только при
создании нового snapshot. Чужой snapshot недоступен. Старые C3/C4A без C4B2
возвращают отсутствие документа, не нулевую доказанную сумму.

JSON запрещает неизвестные поля, повторные ключи, числовые строки, дробные деньги,
пропущенные обязательные поля, null вместо примитивов и trailing tokens. SHA-256
является проверкой целостности, не электронной подписью или доказательством
юридической истинности введённого источника.

## Граница до C4C

V89 добавляет только payroll_snapshot_article153_remuneration: snapshot_id — FK на
C4A, remuneration_authority_id — FK на точную ревизию C4B1. Нет backfill, изменения
старых документов, cascade delete или активации начислений.

finalPayableReady всегда false. Остаются обязательные activationBlockers:
FINAL_PAYROLL_INTEGRATION_REQUIRED, LEGACY_HOLIDAY_RECONCILIATION_REQUIRED,
DOWNSTREAM_EARNING_BASES_REQUIRED. Прежние документы C4A и их blockers не меняются;
C4B2 хранит собственное более полное состояние подготовки.

Следующий этап C4C должен согласовать статутное и местное основания, компонентные
дополнительные суммы, существующий HOLIDAY и NIGHT, исключить двойной учёт,
включить итог в calculationHash, денежные строки и последующие базы начислений.
Только после полной проверки этой интеграции можно активировать HOLIDAY_PAY.

## Проверки

114 целевых Article153Remuneration*Test включают B1 и B2. Денежный движок сравнивается
с независимым целочисленным рациональным oracle на 500 наборах и с прежней часовой
арифметикой. Проверены округление, выбор работника, история без resolver/pricing,
исключения, чужие источники, повреждения, повторные ревизии и откат всех родителей.
Затем обязательны release-check, полный clean verify, прежние JaCoCo-пороги,
PostgreSQL и реальное staging-развёртывание с проверкой result ZIP.
