# P1B3C4A — денежная оценка тарифной части из сохранённых оснований

База C3: `d694a3c43fb21e5499c2d9c39dc5b8349840b197`.
Миграция PostgreSQL: V87. Формат: `ARTICLE153_TARIFF_REFERENCE_V1`.

## Результат и граница

C4A вычисляет и сохраняет две независимые денежные оценки из документа C3:
`STATUTORY_TARIFF_REFERENCE` (тарифная часть сохранённого решения B1) и
`CONFIGURED_LOCAL_REFERENCE` (буквальная оценка сохранённого местного BPS).
Они предназначены для последующего согласования итогового расчёта.

Это не две складываемые выплаты. В документе нет окончательной суммы HOLIDAY_PAY,
нет поля payableAmountMinor и всегда `finalPayableReady=false`.
Значение по местному правилу ещё не доказывает его применимость при выборе
другого дня отдыха. Оно не заменяет решения по всем компонентам оплаты.

Этап не меняет PayrollService, существующие суммы зарплаты, общий calculationHash
или registry HOLIDAY_PAY. У документа есть собственный SHA-256, который связывает
денежную оценку с точным документом C3 и существующей ревизией расчёта.

## Расчёт без нового денежного движка

Используется существующий PayPricingEngine. Для каждой экономической группы:

`hourlyRateMinor × minutes × additionalBps / 600000`, HALF_UP до целой копейки.

Группа определяется видом оценки, сохранённой часовой ставкой и BPS. Фрагменты
с одинаковыми экономическими условиями складываются до округления. ID смены,
причина BOTH, границы дневного/ночного фрагмента не создают отдельных округлений.
Ставки и BPS разных групп не смешиваются. Учитывается только premiumAmountMinor;
возвращаемая движком обычная базовая оплата не добавляется.

Пример: ставка 1 коп./час, 60 минут и +10000 BPS дают 1 коп. Два фрагмента
по 30 минут также дают 1 коп., а не 2. При ставке 50000 коп./час, 60 минутах,
сохранённом B1 +10000 BPS и местном +15000 BPS документ хранит отдельно
50000 и 75000 коп. Складывать их в 125000 коп. нельзя.

Юридическая квалификация, выбор B1, историческая ставка и местный BPS берутся
из замороженного документа C3. Текущая policy и справочники не вызываются.
Новая трактовка статьи 153 или состав обязательных выплат этим этапом не вводится.

## Проверки и воспроизводимость

Документ содержит ID ревизии, её calculationHash, SHA-256 C3, валюту,
версию округления, суммы двух оценок и строки со ссылками на индексы фрагментов C3.
Каждая строка сохраняет ставку, BPS, количество минут, денежный результат и долю
каждого исходного фрагмента. Каждый фрагмент должен входить ровно один раз в каждый
из двух видов оценки. Суммы и количества проверяются отдельно для каждого вида.

Отсутствующее значение, числовая строка вместо числа, отрицательная ставка/BPS,
переполнение, конфликт валют, даты или выбора работника блокируют создание.
Неизвестная классификация компонента не подменяется нулём. При чтении запрещены
неизвестные поля, повторные JSON-ключи, дробная сумма, пропущенные обязательные
поля и неподдерживаемая версия. SHA-256 — контроль целостности, не электронная подпись.

## Сохранение и история

Article153TariffSnapshotService.createRevision создаёт новую PayrollSnapshot,
основания C3 и документ C4A в одной REPEATABLE_READ-транзакции. Ошибка денежной
оценки откатывает уже вставленные родительские записи. У существующей ревизии
нет маршрута перезаписи или автоматического дополнения новыми расчётами.

load(owner, snapshotId) читает только сохранённые записи и проверяет связь
с исходными минутами, ставками и BPS. Числа не пересчитываются текущим движком.
Чужая ревизия недоступна. Старый C3 без C4A возвращает отсутствие документа,
а не нулевую оценку. Формат C3 V1 и его прежние API остаются совместимыми.

V87 добавляет только payroll_snapshot_article153_tariff с внешним ключом на C3,
одной записью на snapshot_id, без backfill и каскадного удаления.

## Оставшиеся условия до активации

1. C4B: доказать полноту системы оплаты и задать денежную применимость INCLUDE
   по компонентам (база, период, пропорция, кратность, выбор дня отдыха).
   Решение INCLUDE из C2 само по себе не определяет такую формулу.
2. Согласовать местное правило с выбором другого дня отдыха; справочный местный
   BPS нельзя автоматически считать окончательным применимым размером.
3. C4C: заменить уже существующую обычную HOLIDAY-доплату, сохранить NIGHT,
   исключить двойной учёт, включить итоговые источники/суммы в calculationHash,
   денежные строки и последующие базы бонусов/коэффициентов.
4. После проверки полного расчёта и истории отдельно активировать HOLIDAY_PAY.

Поэтому документ содержит явные activationBlockers. Пустая конфигурация
компонентов не считается доказательством полноты оплаты работодателя.

## Проверка выпуска

Article153Tariff*Test проверяет арифметику, округление, сохранение, историю,
изоляцию владельцев, откат, повреждение документа и запрет активации.
Затем обязательны release-check, полный clean verify и прежние пороги JaCoCo
70% branches / 88% instructions. Локальная БД тестов — H2; PostgreSQL V87,
frontend и реальное развёртывание проверяются существующим staging workflow.
C4A закрывается только после проверки result ZIP с точным commit/tree и staging.
